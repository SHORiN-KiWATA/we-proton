# 0063：一次路由枚举内复用接口转换

本提案新增；历史测试日期 2026-11-01，公开整理 2026-11-03。[补丁](../../../patches/wine/0063-nsiproxy-Reuse-interface-translations-within-a-route.patch)只修改 Wine `dlls/nsiproxy.sys/ip.c`，保留原作者及 AI 协作署名，必须与 [0062](../0062-nsiproxy-live-interfaces/README.md)配套理解。

## 问题与根因

0062 修正了失效接口身份，但引入性能回退：旧路由 API 每增删一条路由都会先完整枚举路由表；枚举中每行的接口转换又重复执行实时接口查询。大量路由引用同一接口时，相同转换被反复执行。

同一 3000 条合成路由 fixture 下，创建循环由原基底 3.486 秒变为 28.729 秒，删除由 9.124 秒变为 73.152 秒。实际客户端的一次观察中，路由持续减少、结束会话到关闭网卡很快，不支持把整段等待归因为 Wintun 会话关闭挂起。

## 修复和生命周期

每次 IPv4 或 IPv6 路由枚举建立局部映射，第一次遇到某接口名时仍执行 0062 的验证，随后复用成功的 `{name, LUID, index}` 副本。

- 只缓存成功转换，失败不缓存。
- 函数返回即释放；不跨 API 调用、线程或重试使用，不引入 TTL。
- 缓存分配失败时使用已经成功获得的转换结果，不丢弃该路由。
- 不保存 NDIS 内部指针，不增加共享锁；公开接口和写入校验仍保留。
- 同一次枚举不是原子快照。若调用中途同名接口重建，后续行可能使用本次首次观察的身份；下一次调用重新校验。

既有逐路由全表扫描仍然存在。本补丁消除的是重复接口查询的放大，未重写整个路由 API 算法。

## 结果

| 操作 | 原桌面基底 | 仅 0062 | 0062+0063 |
| --- | ---: | ---: | ---: |
| 预热后路由枚举均值 | 3.6932 ms | 28.2934 ms | 3.4666 ms |
| 创建 3000 条路由 | 3.486292 s | 28.729008 s | 3.650596 s |
| 删除 3000 条路由 | 9.124029 s | 73.151918 s | 9.722433 s |

每个版本一次完整循环，全部零探针失败，删除后无测试路由残留，重建后 3000 条。结果是恢复到接近原有水平，不能称为比原版提速八倍，更不能用来推算实际 ping、带宽或整段加速时间。

源代码：[性能探针](../../tests/route_perf_probe.c)、[路由读取探针](../../tests/route_interface_enumeration_probe.c)。合成原始输出与完整结果限制见[验证说明](../../network-integration/VALIDATION.md)。

## 正确性与 Windows 对照边界

接口生命周期/边界 212 项通过。IPv4/IPv6 与双接口删除同名重建的路由语义对比，在 0062 基准和 0063 候选的 PE64、PE32 WoW64 四组中各 194/194，通过数据排序比较；候选自身为两组共 388，不能把包含基准的 776 项都记为候选独立检查。

Wine NSI 双方各 1453 项、0 失败、2 todo。受控 IP Helper 双方各 687 项、相同的 45 个既有失败、6 todo、5 skip；排除两个已知挂起 echo 子函数，不是完整套件全通过。

本次保持上游 [0053 路由 API 修复](../0053-iphlpapi-old-route-functions/README.md)已有的语义及其 Windows 对照依据；没有新增原生 Windows 性能、OOM 或并发热插拔实测。历史正式两架构模块与候选逐字节相同，但 legacy i386 Unix 后端未运行；PE32 使用 WoW64。

## 已排除的误归因与未解决项

未部署 Wintun 会话复用状态的候选改动；当前客户端轨迹是关闭再创建接口，不能拿独立复用实验解释全部卡顿。后续实际捕获的部分广播发送失败来自 raw ICMP，不是先前猜测的 connected UDP 缓存样本；没有为此修改广播权限。

实际多目标加速/停止有一轮成功复测，更早相同版本仍卡住的历史保留。启动前半段的等待未完全定位。没有“所有节点切换已永久解决”的证据。
